# Rev A hardware safety boundary

> **Status: DR-1 input.** This document defines the *logic* of the hardware
> actuation gate. Component selection, thresholds, and timing are DR-2
> outputs. Nothing here is a certification claim; like
> `../R2_ESTOP_SPEC.md`, this is a functional safety element added by the
> integrator, and its final ratings must match measured electricals.

## 1. The enable equation

The external motor drivers are energized only when hardware permission
exists from **every** term of:

```
DRIVER_ENABLE_HW =
    E_STOP_OK_HW
    AND WATCHDOG_OK_HW
    AND MCU_ENABLE_REQUEST
```

The AND is **combined in hardware** (gate/relay/discrete logic — part
selection at DR-2), not in firmware. Firmware contributes exactly one term.

**Firmware requests actuation; it does not possess sole authority to
energize the drivers.** A software-controlled GPIO alone is never a safety
gate: `MCU_ENABLE_REQUEST` is necessary but not sufficient, and the two
hardware terms (`E_STOP_OK_HW`, `WATCHDOG_OK_HW`) can each remove drive
authority with no cooperation from the MCU or from Linux. This extends the
existing spine — `../R2_ESTOP_SPEC.md` R1 ("software-independent") and the
firmware design constraint "the physical E-stop must remove power-stage
authority independently of the MCU" (`firmware/rosmaster-r2/README.md`) —
onto a board Kirra owns.

## 2. Signal definitions

| Signal | Definition |
|---|---|
| `E_STOP_OK_HW` | Hardware permission derived from the **normally closed E-stop loop** (energize-to-run: loop intact → permission present; button pressed, wire cut, or loop power lost → permission removed). Composes with the relay/mushroom/RF chain in `../R2_ESTOP_SPEC.md`. |
| `MCU_WATCHDOG_KICK` | A pulse train generated by MCU firmware while (and only while) its control loop is healthy. |
| `WATCHDOG_OK_HW` | Permission output generated by an **independent external watchdog/supervisor** that monitors `MCU_WATCHDOG_KICK`. Kick absent or wrong → permission removed. The supervisor is a separate device from the MCU (independent of the G474's internal IWDG/WWDG, which remain in use per the firmware's dual-watchdog policy but are not this term). |
| `MCU_ENABLE_REQUEST` | The firmware's actuation **request**. Default inactive: pulled to the disabled state by the board, so it is inactive during and after reset, during bootloader mode, with the Nucleo removed, and whenever firmware has not affirmatively driven it. |
| `DRIVER_ENABLE_HW` | The final hardware permission delivered to the **external** motor drivers' enable inputs. This is the only path by which the drivers may be energized. |
| `E_STOP_SENSE` | **Read-only** MCU status copy of the E-stop loop state. Advisory/observability only — mirrors `../R2_ESTOP_SPEC.md` R6. The stopping mechanism never depends on the MCU reading it. |
| `DRIVER_FAULT_L_N` / `DRIVER_FAULT_R_N` | **Read-only** driver fault inputs from the left/right external drivers (`_N`: active-low assumed pending bench characterization of the retained drivers — verify polarity before DR-2). Firmware treats an asserted fault as grounds to drop `MCU_ENABLE_REQUEST` and report; the fault lines themselves are inputs, never part of the enable drive. |

## 3. Relationship to the existing safety spine

Layered outermost-wins, extending the three-layer picture in
`../R2_ESTOP_SPEC.md` §2:

```
 (1) software MRC: SS-002 decel-to-stop, ADR-0013 request       (unchanged)
 (2) firmware safety state machine: SafetyManager, fail-closed  (firmware tree)
     — drives MCU_ENABLE_REQUEST; bridge_must_be_disabled()
       hard-cuts before any drive decision
 (3) HARDWARE gate on the carrier: DRIVER_ENABLE_HW             (this board)
     — E-stop term and watchdog term each cut drive with
       no software cooperation
```

The firmware safety state machine
(`firmware/rosmaster-r2/docs/SAFETY_AND_PRODUCTION.md`) is the *authority
for requesting* motion (`Active` state only); the carrier hardware is the
*authority for permitting* it. Neither alone energizes a driver.

## 4. Safe-behavior matrix

Every row must result in, or converge to, **disabled actuation**. "Converge"
covers cases where a bounded delay is inherent (e.g. watchdog timeout
window); the bound is measured at bring-up stages 6–7 and 13.

| Condition | Mechanism | Result |
|---|---|---|
| Power-up | `MCU_ENABLE_REQUEST` pulled inactive by the board; watchdog has seen no kick → `WATCHDOG_OK_HW` withheld | Disabled from first power |
| MCU reset (NRST, POR, software reset) | Request line returns to pulled-inactive state; kick stops → watchdog permission drops within its timeout | Disabled |
| Bootloader / DFU mode | Firmware not running → no kick, no request | Disabled |
| MCU crash / hang / stuck loop | Kick stops or degenerates → `WATCHDOG_OK_HW` removed within the supervisor timeout | Disabled (converges within watchdog window) |
| Watchdog timeout | By definition: `WATCHDOG_OK_HW` removed | Disabled |
| E-stop open (pressed, wire cut, loop supply lost) | `E_STOP_OK_HW` removed — hardware path, no software involved | Disabled immediately |
| Nucleo removed / not seated | Request line floats to its board pull (inactive); no kick | Disabled |
| Communication loss (R2CP silent/stale) | Firmware command-freshness gating (`command_timeout_ms`, `valid_for_us` — `firmware/rosmaster-r2/docs/SAFETY_AND_PRODUCTION.md`) enters ControlledStop and drops `MCU_ENABLE_REQUEST`; independent of that, a wedged firmware is caught by the watchdog term | Converges to disabled |
| Jetson restart | Same as communication loss at the MCU; the Jetson side re-establishes authorization through the unchanged verifier/consumer chain before any new command | Converges to disabled |

Notes:

- Rows that rely on firmware behavior (communication loss) are *also*
  backstopped by a hardware term — the design never depends on a single
  software mechanism to reach the safe state.
- "Disabled actuation" for Rev A means `DRIVER_ENABLE_HW` withdrawn at the
  external drivers' enable inputs. Behavior of the retained drivers when
  disabled (coast vs. brake) **requires bench characterization** and is
  recorded at bring-up stage 8 — the firmware tree's H-bridge truth-table
  inspection requirement carries over
  (`firmware/rosmaster-r2/docs/HARDWARE_REFERENCE.md` §Motor bridge).
- The steering gear's behavior on disable (unpowered hold vs. cut) follows
  the open question already recorded in `../R2_ESTOP_SPEC.md` §5.

## 5. What this gate does NOT do

- It does not authorize motion. Authorization stays with the Kirra
  verifier/governor and the ADR-0033 consumer; link authentication stays
  with R2CP `AUTH_TAG`; this gate is the actuation-side backstop.
- It does not protect against a privileged process or physical access on
  the Jetson side — the serial single-writer discipline is operational, not
  adversarial, and that limitation is unchanged by Rev A.
- It does not remove the need for the firmware safety state machine; the
  hardware gate is deliberately coarse (enable/disable), and controlled
  deceleration remains firmware's job while permission is present.
- Timing claims (E-stop-to-disable latency, watchdog window) are **made
  only from measurements** at bring-up, never from this document — the
  same rule the firmware tree applies to all timing
  (`firmware/rosmaster-r2/docs/ROADMAP.md` preamble).
